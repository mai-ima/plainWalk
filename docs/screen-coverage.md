## 保存データを保護する撮影

`-PlainWalkScreenshotFixture` を指定した DEBUG 起動だけが、新しい一時フォルダへ合成データを作ります。通常の保存領域を読み替えたり上書きしたりしません。写真はコードで描いた検証用イラスト、座標は公開地点周辺の計算値で、実際の歩行や写真ではありません。HealthKit や現在地の許可を勝手に要求せず、実データの取得に成功したとは扱いません。

`scripts/native-screen-catalog.json` が追加の区間一覧、`capture-native-screens.py` が起動と撮影、`check-native-captures.swift` が本文の文字確認です。プロセス起動と画面表示の待ち時間を分け、毎回古い完了ファイルを削除します。スクロールは要求後のマーカーだけで成功とせず、画像の文字も確認します。バッジ詳細は実際の境界集計が終わるまで待ちます。

実装済みのページ・表示は [40 表示の在庫](native-screen-inventory.md)で追えます。撮影枚数は別ページの数ではなく、空・記録あり・編集・確認・スクロール区間を含む数です。

Web は `npm run build` の後に `node scripts/capture-web-screens.mjs` で再撮影します。Native の最新画像の確認後、`node scripts/prepare-screen-gallery.mjs` で `artifacts/previews/native-all/manifest.json` と `web-all/manifest.json` から配信用一覧を作ります。画像は元の撮影フォルダにあるものだけを採用します。

## 別途確認が必要な範囲

OS のカメラ、写真・ファイル選択、共有先、位置・通知・HealthKit の権限、実際のロック画面・Dynamic Island は、アプリの一覧画像とは別に実機で確認する必要があります。実データのない Simulator で、許可や撮影が成功した画像を作りません。すべての色・メニュー・アニメーション・入力状態の組み合わせを網羅したものでもありません。

Watch、通常ウィジェット、自動開始、近接交換、クラウド招待・同期、本家の素材仕上げ、1 日複数のノートなどの未実装部分は、架空の画面を作って対応済みにしません。


## 検証中に直したこと

初回の追加撮影は、ノートと記録下部で撮影用引数が一致していませんでした。引数を統一し、古い完了ファイルを削除して再撮影しました。起動コマンドが時間超過しても、新しく書かれた起動通知がある場合に限って、その後の実表示と画像の文字を独立に確認します。起動通知だけで撮影成功にはしません。

プロフィール下部は正しく表示されていましたが、Vision が「設定」を取り逃しました。下部の長い固有ラベル「バックアップを書き出す」で確認するようにしました。一方、ノート下部は実際に足りず、複数の子を持つ Group の ID ではなく、末尾の共有 Button の実矩形へスクロールするよう修正しました。修正後の画像で全スライダーと共有ボタンを確認しています。条件を緩めて古い画像を成功扱いにしていません。

撮影済み画像の再確認は `Review native screen captures` ワークフローで行えます。出典・画像の存在・画面と状態の一致を検査してから、現在のラベルで文字確認をやり直します。元の判定を残し、欠けた画像や別状態を補ったことにはしません。

旧 200 枚一覧の検索・分類・拡大・前後・戻る・入力サイズ・横はみ出しは、Chromium に加え Linux WebKit の 393 × 852・タッチ設定でも確認しました。更新後の一覧は公開前に改めて確認します。実際の iPhone のピンチ・Safari・権限・ロック中記録は未検証です。
